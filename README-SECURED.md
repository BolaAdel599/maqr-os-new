
# Maqr OS

نظام SaaS لإدارة مطاعم متعدد المستأجرين (QR ordering, POS, KDS, دليفري, سوبر أدمن).

> ملاحظة: النسخة اللي اسمها "VERIFIED-10X" اللي جاية قبل دي كانت بتدّعي إصلاحات أمنية مش
> متطبقة فعليًا في الكود. الملف ده وملف `CHANGES.md` بيوثّقوا الوضع الحالي الحقيقي بعد المراجعة.

## الوضع الحالي (بعد المراجعة والإصلاح)

- تحقق Paymob HMAC حقيقي (HMAC-SHA512 + constant-time compare)، والـ webhook بيرفض (fail-closed)
  لو الـ secret مش متظبط.
- عزل كل API حسب `restaurantId` + جلسة NextAuth حقيقية (مش مجرد ادّعاء).
- السعر والكمية بيتحسبوا/يتحددوا سيرفر-سايد من قاعدة البيانات، مش من العميل.
- قفل محاولات كود التوصيل DB-backed (مش in-memory).
- `middleware.ts` بيحمي `/kitchen` `/cashier` `/driver` `/super` فعليًا بالدور المناسب.
- Pusher / WhatsApp Cloud API / Cloudflare R2: تكاملات حقيقية تشتغل لو المفاتيح متظبطة في `.env`
  (شوف `.env.example`)، وبترجع fallback واضح (polling / console log / خطأ صريح) من غيرهم.
- Vercel Cron متظبط في `vercel.json` عشان `/api/cron/check-subscriptions` يتنفذ يوميًا.
- شاشة إدارة منيو كاملة على `/admin/menu` (أقسام، أصناف، صور، تفعيل/تعطيل).
- تدفق دفع Paymob كامل (مش بس استقبال الـ webhook) لكل من أوردرات الترابيزة والدليفري، مع
  إعادة إرسال رابط الدفع (من العميل نفسه لو قفل الصفحة بالغلط، أو من الأدمن عبر واتساب لو ضاع
  منه الرابط خالص).
- أوردرات دليفري: الكاشير يقدر ينشئ أوردر دليفري (اسم/موبايل/عنوان)، وبعد ما المطبخ يخلص
  (`READY`) يعين طيار متاح من قايمة حقيقية، والطيار ياخد كود تحقق حقيقي (اتولّد وقت إنشاء
  الأوردر ويتبعت واتساب للعميل لو مفعّل).
- الأوردرات المعلقة (`AWAITING_PAYMENT`) بتتلغي تلقائيًا بعد ٣٠ دقيقة (كرون)، أو الأدمن يقدر
  يلغيها أو يعيد إرسال رابطها بنفسه من `/admin/payments`.

## لسه ناقص / معروف

- `Table.qrToken` موجود في الـ schema بس مفيش استخدام له في التحقق من صحة رابط الـ QR (أي حد
  يقدر يفتح `/t/5` مباشرة من غير ما يكون ماسح كود QR حقيقي - ده سلوك متعمد عادة في الأنظمة دي،
  بس لو عايز تمنع الوصول المباشر، محتاج تتحقق من `qrToken` كـ query param).
